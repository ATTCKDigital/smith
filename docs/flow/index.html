New Feature Workflow:

Smith’s first job is to understand what it’s been asked to do. It sorts the input into one of four categories — a question (answered immediately, no workflow started), a bug fix, a new feature build, or an investigation. This routing decision determines everything that follows.

  • Questions are answered directly and the workflow never starts
  • Bug fixes route to a streamlined path with no planning phase
  • New features route to the full workflow including requirements gathering
  • Investigations route to a diagnostic-only mode that produces a report
  • Hook: task-router.sh (UserPromptSubmit) runs before Claude sees the message and routes to /smith-new, /smith-bugfix, /smith-debug, or /smith-bank based on trigger phrases

Once classified as a build or fix command, Smith creates a completely isolated copy of the codebase. This sandbox is separate from the live project — nothing that happens during development can affect the main branch until it is explicitly reviewed and merged. The user’s current working directory is never touched.

  • A unique branch name is generated from the task description (2–4 words)
  • An isolated workspace is created from the latest main branch
  • A workflow tracking marker is registered so progress can be recovered if interrupted
  • All subsequent file writes are locked to this workspace only
  • Invoked by /smith-new or /smith-bugfix; create-active-workflow.sh registers the tracking marker; workflow-gate.sh (PreToolUse) blocks writes until the marker exists

Before the rubric scores the work, three automated quality passes run in sequence directly on the implementation. Each pass can modify the code — findings are applied, not just reported — so the rubric evaluates the finished, corrected result.

  • /code-review — scans for correctness bugs: logic errors, missing edge cases, misused APIs, and anything that would cause incorrect behavior at runtime
  • /simplify — reviews for reuse, simplification, and efficiency cleanups; applies them directly to the working tree before moving on
  • /security-review — security-focused scan covering auth checks, data escaping, injection risk, capability verification, and anything that could expose a vulnerability
  • All three are orchestrated by /smith-clean-code — each pass applies its fixes before the next runs; output is a modified working tree, not a report

An independent critic — a separate AI process with no prior involvement in building or reviewing the feature — scores the entire body of work against a 100-point quality rubric. This is the final objective check before anything is merged.

  • 7 rules, each weighted by importance — 100 points total
  • All-or-nothing scoring per rule: one failed sub-criterion zeros the whole rule
  • Must score exactly 100 to pass — no partial passes
  • The critic has no involvement in writing or reviewing the code it scores
  • The critic is claude-haiku, running externally via stamp-response.sh + workflow-summary.sh (Stop hooks) — a process completely separate from the one that built the feature

If the rubric score falls below 100, the specific issues are identified, fixes are applied automatically, and the rubric runs again. This can repeat up to three times. If the work still fails after three cycles, the workflow halts and surfaces the remaining issues to the user rather than merging broken code.

  • Each retry re-reads the rubric findings to understand exactly what failed
  • Targeted fixes are applied — not a full rewrite
  • The rubric runs again on the corrected code
  • After 3 failed cycles, the user decides what happens next

  • Commit message follows Conventional Commits format (feat:, fix:, etc.)
  • Pull request includes a summary, what changed, and a test plan checklist
  • Branch is merged and deleted automatically
  • The isolated workspace is removed after a successful merge

How it works:

Multiple AI agents work simultaneously, each focused on a specific domain — dramatically compressing review time without sacrificing depth.

Rubric failures trigger automatic correction cycles before anything ships. Completed features write lessons to a persistent knowledge base, improving future work automatically.

Governance files are loaded at the start of every step. Isolated worktrees prevent changes from touching the main codebase until review is complete.

Fast, cheap models handle routine tasks; powerful models are reserved for complex reasoning — keeping costs efficient without sacrificing quality.

Every agent action, decision, and outcome is logged to a session vault. A complete record of how every feature was built is always available.
